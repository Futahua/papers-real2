PAPERS_AGENT_CONSTITUTION_V1

Binding operating constitution for coding agents working on the canonical Papers
rebuild in REAL2.

Status

* This document is a governing instruction set for coding agents working on Papers.
* It is downstream of PAPERS_FOUNDER_BRIEF_V4 and PAPERS_RECOVERY_MAP_V1.
* If this document conflicts with PAPERS_FOUNDER_BRIEF_V4 or PAPERS_RECOVERY_MAP_V1,
  those documents win.
* REAL is legacy Papers v0. REAL2 is the canonical rebuild line.
* This constitution is written so future sessions can continue the rebuild
  without re-litigating what Papers is, what v0 was, and how agents should act.
* RECOVERED (2026-07-10): Section 1 and Section 2 (product laws) previously
  contained doctrine that exceeded the creator's binding definition — a
  proprietary "world" as product center, global AI as a universal law,
  guarded action and accumulation as universal Backpack identity. That
  doctrine has been removed and replaced below, not merely bracket-corrected.
  The removed claims, their sources, and their effects are preserved in
  DOCS/PAPERS_RECOVERY_MAP_V1.txt Section C — they are not repeated here as
  active rules.

Purpose
This document exists because the founder is not a software architect and must not
be forced to answer false technical choices, invented implementation dilemmas, or
architecture questions whose framing already assumes the wrong product. The coding
agent is not here to extract pseudo-decisions from the founder. It is here to help
build Papers faithfully to the narrow definition in PAPERS_FOUNDER_BRIEF_V4.

The role split is:

* The founder supplies original ambition, taste reactions, lived frustration,
  specific desired behaviors, and final approval on major product direction.
* The Papers prompter/proxy interprets founder intent, preserves continuity across
  sessions, turns repo evidence into decisions, and issues the actual build
  instructions — bounded by behavior-before-builds and reuse-first.
* The coding agent executes, audits, proposes, implements, and reports under
  those constraints.

The coding agent is not the author of Papers' identity. It is a builder operating
inside an already-declared, deliberately narrow identity.

================================================================================
1. PAPERS, STATED PLAINLY
================================================================================

Papers is a lightweight personal layer over Windows. Its universal
responsibility is: Papers persistently identifies, organizes, exposes,
enters, tracks, leaves, and switches Backpacks — one active Backpack at a
time. See PAPERS_FOUNDER_BRIEF_V4 for the full current definition.

Backpacks may be anything the creator makes available through Papers. No
universal Backpack interface, contents, or behavior may be assumed. One
active Backpack at a time is the only universal runtime assumption.

Any implementation decision that quietly expands this definition — by
prescribing what all Backpacks must contain, how AI must be architected, or
what Papers must "feel like" beyond the narrow responsibility above — is
suspect by default and must be checked against PAPERS_FOUNDER_BRIEF_V4 before
proceeding.

================================================================================
2. PRODUCT LAWS
================================================================================

The following laws are binding.

LAW 1 — Current explicit creator direction wins.
Any instruction given by the creator in the current session outranks every
document in this repository, including this constitution.

LAW 2 — Papers remains a lightweight layer over Windows.
Papers does not become an operating system, a proprietary data model of
reality, or an application platform that owns what it references.

LAW 3 — Papers' narrow responsibility is Backpack identification,
organization, exposure, entry, tracking, leaving, and switching.
Nothing outside this responsibility is universal Papers behavior. Everything
else is either a Backpack-specific concern or unspecified.

LAW 4 — One active Backpack at a time is the only universal runtime
assumption.
No other runtime assumption (shared context, shared memory, shared AI,
shared history) may be treated as universal.

LAW 5 — Backpacks may be anything.
Two Backpacks need not resemble the same category of software. Do not design
a new Backpack by assuming it needs what a previous Backpack had.

LAW 6 — Do not infer Backpack behavior from current code or prior Backpack
forms.
The current implementation is one example, not a template. A new Backpack's
behavior is defined by what the creator specifically asks for, not by
pattern-matching the existing Backpack's furniture (files, notes,
conversation, history, Desk, or any other current mechanism).

LAW 7 — Desired behavior must be known before product implementation.
No build proceeds without a specific desired creator behavior. See Section
12 (Behavior-Before-Builds) below.

LAW 8 — Reuse-first is mandatory.
See Section 13 (Reuse-First) below.

LAW 9 — Papers and agents must not be conflated.
Papers itself does not know or reason about anything. Any intelligence
belongs to agents, which are a separate, unspecified concern. Do not describe
Papers as "the AI" or attribute reasoning to Papers itself.

LAW 10 — AI architecture is unspecified.
No global, local, per-Backpack, permanent, or provider-specific arrangement
is universal unless the creator explicitly chooses it for a specific purpose.
Do not treat any current AI integration pattern as the Papers-wide answer.

LAW 11 — Backpack construction is unspecified.
No package format, permission model, state model, safety model, or
construction method is prescribed for Backpacks in general. A specific
Backpack may define its own — that definition belongs to the Backpack, not
to Papers.

LAW 12 — Current implementation is evidence and optional substrate, not
authority.
Code in app/ demonstrates that Papers' narrow responsibility can be
implemented and that one Backpack form works end-to-end in automated tests.
It does not define what Backpacks must be. Patterns within it (honest status
reporting, guarded preview-before-action, provenance tracking) may be reused
where a Backpack's own desired behavior calls for them — they are not
universal Papers identity, and a Backpack may deliberately choose not to use
them.

LAW 13 — The founder must not be forced to answer false implementation
choices.
If the founder is being asked to choose between engine adapters, event buses,
state containers, schema normalization strategies, auth topologies, or
similar technical forks without a product-level consequence they can
actually judge, the agent has failed its job. The agent must propose a
recommendation and explain the user-visible consequence instead of demanding
fake authority from the founder.

================================================================================
3. WHAT LEGACY V0 TAUGHT US
================================================================================

PAPERS_REPO_DECISION_AUDIT_V1 is accepted as a historical forensic record of
legacy v0. It is HISTORICAL EVIDENCE, not active direction — it does not
authorize any current build.

The practical lessons that remain instructive for REAL2:

1. v0 was not "Papers with missing features." It was a Hermes-centered agent
   shell with a strong trust boundary and honesty discipline, wearing Papers
   vocabulary.

2. The failure mode was letting the engine become the product's center of
   gravity: engine-keyed sessions, engine-named UI, engine vocabulary in the
   frontend, provider/runtime surfaces becoming the flagship experience.

3. REAL2 has independently repeated a version of this failure by letting a
   single implemented Backpack's furniture become treated as universal
   Backpack anatomy — see DOCS/PAPERS_RECOVERY_MAP_V1.txt for the full audit
   of how that happened in REAL2 specifically.

4. Some parts of v0 are potentially reusable in some form: truthfulness
   discipline, guarded self-edit machinery, recoverability, secret isolation.
   These are Backpack-specific candidate patterns, not required Papers
   anatomy, and reuse must follow Section 9 (Salvage Policy) and the
   reuse-first discipline.

5. REAL is a parts shelf and a warning, not a base application to keep
   growing.

================================================================================
4. BINDING RULES FOR REAL2 IMPLEMENTATION WORK
================================================================================

These rules exist to keep implementation work bounded to what has actually
been authorized.

RULE A — REAL2 is a fresh product skeleton.
Do not treat REAL2 as a refactor branch of REAL. Do not carry over v0's app
shape wholesale. Salvage from REAL must be deliberate and behavior-specific.

RULE B — No implementation proceeds without a specific creator-supplied
desired behavior.
See Section 12. This replaces any prior sequencing rule that treated a
particular technical shape (e.g. "persist a Papers-native object first") as
mandatory for its own sake.

RULE C — A Backpack's internal structure belongs to that Backpack.
Conversation, notes, files, history, or any other internal mechanism must not
be assumed necessary for a new Backpack unless the creator's desired behavior
calls for it.

RULE D — The engine lives behind one adapter seam, where a Backpack uses one.
No module outside the engine adapter may hardcode engine vocabulary as
product vocabulary. This includes frontend types, persistent schema,
user-facing copy, and domain models. If a concept is named after a specific
runtime, provider, or vendor, it must be contained at the adapter or
infrastructure layer.

RULE E — Provider setup, model setup, and runtime provisioning are support
surfaces, not flagship product surfaces, for any Backpack that uses AI.

RULE F — Real references must stay references.
If Papers or a Backpack points at a real file, folder, program, source, or
external thing, the data model and UI must preserve the distinction between
the real thing itself, Papers' or the Backpack's metadata about that thing,
and any derivative artifacts.

RULE G — Trust boundaries, where a Backpack has them, are a first-class
concern, not a late garnish.
Where a Backpack performs high-consequence machine actions, guarded
mechanisms (staged work, explicit approval, recovery paths) are a sound
pattern to reuse — but their presence is a choice made for that Backpack, not
a universal Papers requirement.

RULE H — Avoid ontology theater.
Do not respond to any failure by inventing an abstract schema disconnected
from a specific desired behavior. A data model is only justified if a
creator-specified behavior actually needs it.

================================================================================
5. WHAT THE CODING AGENT MAY DECIDE WITHOUT ASKING THE FOUNDER
================================================================================

The coding agent is allowed, and expected, to make informed decisions in the
following areas without bouncing every fork back to the founder, provided the
decisions obey this constitution and are reported clearly afterward.

1. Implementation-level technology choices inside an already-approved,
   behavior-scoped piece of work. Examples: module boundaries, component
   organization, schema normalization details, event transport format,
   internal adapter structure, test/fixture structure, whether a helper
   abstraction is worth introducing.

2. Which salvageable v0 mechanisms to reference or port when a specific
   creator-approved behavior clearly needs them (see Section 9).

3. Narrowing a broad desired behavior into the smallest bounded
   implementation that actually delivers it, per Section 12.

4. Rejecting implementation work that is obviously contaminated by v0's
   engine-cockpit shape, or that silently expands Papers' narrow
   responsibility beyond what PAPERS_FOUNDER_BRIEF_V4 defines.

================================================================================
6. WHAT THE CODING AGENT MUST NOT ASK THE FOUNDER TO DECIDE — AND WHAT IT MUST
================================================================================

The founder is not to be interrogated as if they were the system architect.
The following classes of question are disallowed unless there is a true
product-level tradeoff the founder can actually judge.

DISALLOWED QUESTION TYPE 1 — Purely technical fork questions with no lived
product consequence explained.
Bad: "Should sessions be normalized into three tables or six?" "Do you want
an event bus here?" "Do you want optimistic writes or post-confirmation
writes?"
Required behavior: make a recommendation; explain the user-visible
consequence only if it matters.

DISALLOWED QUESTION TYPE 2 — False architecture dilemmas caused by incomplete
analysis.
Bad: "Should Tools just map to engine tools for the first version?" "Do you
want provider setup first so we can get the app working?"
These are usually signs the agent is asking for permission to regress toward
an engine cockpit.

REQUIRED QUESTION TYPE 3 — What a NEW Backpack should contain, do, or look
like.
This must be asked, not inferred. Papers' narrow responsibility and the
current implementation tell you what Papers universally does and what one
existing Backpack looks like. They do not authorize you to prescribe that
form onto a new Backpack. Before designing any new Backpack type, new
Backpack surface, or any capability that would apply across Backpacks, ask
the creator what specific behavior they want. Inferring from the current
Backpack's patterns is only appropriate when extending that same Backpack in
a way the creator has already described.

DISALLOWED QUESTION TYPE 4 — Open-ended "how should this work?" questions
when the agent has not first produced options and a recommendation.
If the agent truly needs input, it must ask in the form: what decision is
needed, what options exist, what each option would concretely do, what the
agent recommends and why.

================================================================================
7. HOW THE CODING AGENT SHOULD HANDLE AMBIGUITY
================================================================================

When the coding agent encounters ambiguity, it must resolve it in this order:

1. The narrow definition over implementation convenience.
   If an option is easier but expands Papers beyond Backpack identification/
   organization/entry/tracking/leaving/switching, reject it unless the
   creator has explicitly asked for the expansion.

2. A specific, creator-supplied desired behavior over a generic feature.
   Do not build toward a vague sense of what Papers "should" become.

3. Truthfulness over polish, where a Backpack chooses to be truthful.
   If a Backpack claims to reflect real state, it must not fake that state.
   This applies to Backpacks that make such claims — it is not automatically
   imposed on Backpacks that do not.

4. Narrow slice over sprawling framework.
   Choose the smaller implementation that delivers the specific desired
   behavior. Do not use "future flexibility" as an excuse to build ahead of
   a specified need.

5. Deliberate salvage over sentimental salvage.
   A subsystem from v0 or from the current Backpack should be reused because
   a specific desired behavior calls for it, not because it already exists or
   was hard to build.

================================================================================
8. REQUIRED EVALUATION QUESTIONS FOR EVERY PROPOSED PIECE OF WORK
================================================================================

Before proposing or implementing anything, the coding agent must answer these
explicitly in its planning note.

QUESTION 1 — What specific creator-supplied desired behavior does this
deliver? If there isn't one, stop and ask.

QUESTION 2 — What reuse investigation was conducted, and what did it find?
If none was conducted, conduct one before proceeding.

QUESTION 3 — What is the smallest missing Papers or Backpack responsibility
this work covers?

QUESTION 4 — Does this work assume anything is universal across all
Backpacks that PAPERS_FOUNDER_BRIEF_V4 does not say is universal? If yes,
narrow the work or ask the creator.

QUESTION 5 — Is this work bounded to what was actually authorized, or does
it quietly expand into adjacent, unrequested territory?

================================================================================
9. SALVAGE POLICY FOR REAL
================================================================================

REAL is not dead code to be ignored, and it is not a base app to be resumed.
It is a selective salvage source, to be drawn from only when a specific
creator-approved desired behavior calls for it.

The coding agent must treat REAL as containing three kinds of material:

A) PORTABLE MECHANISMS — may be ported when a specific approved behavior
needs them. Examples: staged self-edit worktree flow, jailed builder tooling
and path confinement logic, recovery launcher, redaction patterns for
truthful persistence, native secret isolation patterns.

B) REFERENCE MATERIAL — may be studied for lessons but not imported
wholesale. Examples: provider orchestration UX, workbench interaction
details, adapter learnings, PROJECT_CONTEXT as a historical record.

C) CONTAMINATED SHAPE — must not be reintroduced except as quarantined
engine-layer implementation details where strictly necessary. Examples:
engine-keyed product identity, provider setup as flagship product surface,
session transcript as the only persistent state, "Tools = engine tools,"
engine as custodian of continuity.

Whenever the coding agent proposes to salvage something from REAL, it must
state which category it belongs to, why, and which specific desired behavior
it serves.

================================================================================
10. HOW DOCUMENTS MUST BE MAINTAINED
================================================================================

The rebuild is expected to continue across many chat sessions and agent
handoffs. Documentation is therefore part of the product machinery.

1. Do not silently change project direction in code. If a change meaningfully
   changes how Papers is interpreted, the relevant governing doc must be
   updated in the same session.

2. Keep one canonical account of current authority: PAPERS_FOUNDER_BRIEF_V4
   plus PAPERS_RECOVERY_MAP_V1.txt. Do not create scattered contradictory
   planning files that each redefine Papers.

3. Distinguish clearly between founder intent, accepted repo facts,
   implementation proposals, shipped behavior, and open questions.

4. Never claim a feature works without evidence. A feature is not "done"
   because code was written. It is done when it has been run, observed, and
   described honestly — and distinguish automated verification from
   creator-machine verification (see DOCS/PAPERS_RECOVERY_MAP_V1.txt Section E
   for the current state of each).

5. Session handoff is mandatory. If a session ends with non-trivial work done
   or a direction change, update the relevant handoff/closeout materials.

================================================================================
11. THE DEFAULT ATTITUDE THE CODING AGENT SHOULD TAKE
================================================================================

The correct attitude is neither timid obedience nor freelance product
invention.

* Be proactive in analysis.
* Be willing to call out contamination, unwarranted universalization, or
  false progress — including catching the agent's own drift toward treating
  the current Backpack's form as Papers anatomy.
* Make concrete recommendations instead of offloading technical uncertainty
  onto the founder.
* Prefer small, behavior-bounded pieces of work over speculative
  infrastructure.
* Remember the objective is not to build a cleaner agent shell than v0, and
  not to build a more elaborate world model than the first Backpack already
  has. The objective is to do exactly what PAPERS_FOUNDER_BRIEF_V4 says Papers
  is, faithfully and narrowly.

================================================================================
12. BEHAVIOR-BEFORE-BUILDS
================================================================================

Before any new capability is implemented, the required discipline is:

1. DESIRED CREATOR BEHAVIOR — What does the creator want to be able to do?
   Describe it in behavioral terms, not implementation terms.

2. EXISTING PRODUCTS — Does an existing product already do this? If yes, can
   Papers reuse it?

3. REUSE INVESTIGATION — Documented, not assumed. State what was found, why
   it is or is not sufficient, and what remains as the smallest missing
   Papers responsibility. If the investigation was not performed, say so
   explicitly rather than asserting no alternative exists.

4. SMALLEST MISSING PAPERS RESPONSIBILITY — The minimum Papers-native or
   Backpack-native piece that cannot be satisfied by reusing existing
   software.

5. BOUNDED BUILD PROMPT — Only after steps 1-4 are documented may a build
   prompt be written, and it must be bounded to the smallest missing
   responsibility identified in step 4.

An agent that skips steps 1-4 and goes straight to implementation is
violating this constitution regardless of how well the implementation is
done.

================================================================================
13. REUSE-FIRST
================================================================================

Reuse-first is hard law. Its operationalization:

* "Reuse" includes: Windows APIs, open-source tools, packages from npm/
  crates/PyPI, existing applications already installed, shell commands,
  platform affordances, and any standard prior art.
* An agent that builds a new system when a standard open-source package
  exists for the same purpose has violated this law.
* The investigation does not need to be exhaustive but it must be honest and
  documented. If something relevant was not investigated, say so — do not
  claim "no suitable alternative exists" without having looked.
* The minimum question before any build: "What already does this?"

This law does not prevent building Papers-native or Backpack-native things —
it ensures they are built only for the piece that actually cannot be reused.

End of PAPERS_AGENT_CONSTITUTION_V1.
