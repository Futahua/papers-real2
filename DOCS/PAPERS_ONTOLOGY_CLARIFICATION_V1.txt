PAPERS_ONTOLOGY_CLARIFICATION_V1

Canonical vocabulary for REAL2: PAPERS vs BACKPACK vs TOOL, and the status of
"world" / "room" as historical implementation labels.

Status
- CORRECTED AND ACTIVE. Originally issued 2026-07-09 to correct a "room" vs
  "Backpack" vocabulary drift. Revised 2026-07-10 to also remove "World" as
  active product ontology, per PAPERS_FOUNDER_BRIEF_V4 and
  DOCS/PAPERS_RECOVERY_MAP_V1.txt.
- The original version of this document (2026-07-09) treated "World" as a
  canonical governing concept with a fixed hierarchy of universal Backpack
  children (contents, surfaces, activity, artifacts, AI context). That
  content exceeded the creator's binding definition and has been removed
  from this document, not merely annotated. It is preserved as superseded
  doctrine in DOCS/PAPERS_RECOVERY_MAP_V1.txt Section C, Drift 11.
- Authority: downstream of PAPERS_FOUNDER_BRIEF_V4; binding on implementation
  vocabulary, docs, and UI copy.

================================================================================
1. ACTIVE VOCABULARY
================================================================================

PAPERS
The lightweight layer over Windows that persistently identifies, organizes,
exposes, enters, tracks, leaves, and switches Backpacks — one active Backpack
at a time. Papers does not own, model, or semantically represent the
surrounding machine or reality beyond what this responsibility requires.

BACKPACK
Anything the creator manually makes available through Papers as a distinct
place to enter or invoke. Backpacks may be anything. No universal Backpack
interface, contents, or internal structure is prescribed. A Backpack's
internals, construction, and behavior are defined by what that specific
Backpack is for — not by Papers, and not by any other Backpack.

TOOL
A simpler capability that the creator manually categorizes as a Tool rather
than a Backpack. This is an organizational choice the creator makes, not a
technical distinction Papers enforces.

================================================================================
2. CURRENT IMPLEMENTATION LABELS (not product ontology)
================================================================================

The words "world" and "room" appear throughout the current codebase and
persisted data: WorldStore, world.json, roomId, room.json, IPC channels
(room:get, room:say, ...), artifact kind "room-note", activity event kinds
(room-created, room-renamed, ...), and the CSS/UI labeled "world view."

These are historical implementation identifiers from when the project used
"world" and "room" as active product concepts. They remain in code and
persisted data as labels only. They are not product ontology and must not be
read as defining what Papers or a Backpack fundamentally is.

Practical handling:
- No ceremonial mass-rename of working code is required by this document.
- New code, new persisted schema, new IPC channels, and new modules should
  prefer Backpack-native naming where it does not create unnecessary schema
  churn for no behavioral benefit.
- Historical activity events persisted with old "room" wording are a
  truthful record and are not rewritten.
- User-facing and AI-facing language must say "Backpack," not "room" or
  "world," regardless of what the underlying code calls it.

================================================================================
3. NAMING RULES
================================================================================

PRODUCT LANGUAGE (UI copy, docs, milestone framing, AI-facing context):
Say Papers, Backpack, Tool. Do not say "world" as a product concept. Do not
use generalized "room" vocabulary as the primary noun.

IMPLEMENTATION TOLERANCE:
Code identifiers, IPC channel names, persisted schema labels, and CSS class
names may continue to use "room" and "world" as internal labels without
requiring a rename. This is a documented decision, not drift, as long as
user-facing and AI-facing copy says Backpack.

================================================================================
4. OPERATIONAL RULES FOR AGENTS
================================================================================

1. Treat the currently implemented "room" as one existing Backpack
   implementation, not as a template for what Backpacks must be.
2. Do not let "world" or "room" vocabulary reappear as an active product
   concept in new documents, UI copy, or AI-facing context.
3. Do not assume a new Backpack needs the current Backpack's contents,
   surfaces, activity log, artifacts, or AI context. Those are specific to
   the current implementation — see DOCS/PAPERS_RECOVERY_MAP_V1.txt Section F
   for their classification.
4. If code, UI, or documentation starts reinforcing "Papers is fundamentally
   a world/room app," or that all Backpacks share one hierarchy of children,
   call it out as drift and correct it, don't just annotate it.

End of PAPERS_ONTOLOGY_CLARIFICATION_V1.
