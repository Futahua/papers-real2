B. CORRECT PRODUCT BOUNDARY
================================================================================

The following is the binding creator definition. It outranks every other
document in this repository. Do not enlarge it.

  Papers is a LIGHTWEIGHT PERSONAL LAYER OVER WINDOWS.

  Windows, applications, files, folders, projects, services, scripts, the
  machine, and outside data already exist independently beneath it. Papers
  does not own them, absorb them into a proprietary World, semantically
  model all of them, or replace them.

  Papers' universal governing responsibility is:

    Papers persistently identifies, organizes, exposes, enters, tracks,
    leaves, and switches Backpacks — one active Backpack at a time.

  That is intentionally close to all Papers universally is.

BACKPACKS
  A Backpack is anything the creator manually chooses to make available
  through Papers as a distinct place to enter or invoke.
  Backpacks may be literally anything.
  Two Backpacks must not be assumed to resemble the same category of software.

  No universal Backpack assumptions may be made about:
    interface; contents; dashboard; Desk; notes; files; chat; history;
    artifacts; lifecycle; restoration; state model; permission model;
    rendering; package format; construction method; resource behavior;
    AI integration; safety model; background behavior; definition of success.

  One active Backpack at a time is the only universal runtime assumption.

TOOLS
  A Tool is a simpler capability the creator manually chooses to classify
  as a Tool rather than a Backpack. This is an organizational decision made
  by the creator. Papers should not enforce a deep technical ontology
  separating Tools from Backpacks.

AI AND AGENTS
  Papers itself does not "know" anything.
  Agents may know whatever deliberately engineered context, tools, access,
  and integrations permit. The implementation may use local agents, external
  agents, coding agents, open-source agents, hosted models, Backpack-specific
  systems, or combinations.
  Papers must not prescribe: one global Papers AI; one permanent AI identity;
  permanent World-level memory; universal Backpack context; AI in every
  Backpack; AI-created Backpacks; or one provider or runtime.
  Papers must not be described as the intelligence itself.

REUSE-FIRST
  Before building substantial functionality:
    1. identify suitable existing open-source products;
    2. consider forks, configuration, plugins, composition, automation;
    3. write new code mainly for missing glue, adaptation, presentation,
       or genuinely unavailable behavior.
  Do not rebuild inferior internal versions of existing products.

BEHAVIOR BEFORE BUILDS
  Future work must proceed: desired creator behavior → existing products
  and systems → reuse investigation → smallest missing Papers responsibility
  → implementation. If desired behavior is unspecified, ask. Do not issue
  a build prompt.

Source      : README.md, section "What Papers is (non-negotiable)"
Quotation   : "Its center of gravity is the Papers world model, not an
               agent engine."
Type        : [AI INTERPRETATION] based on founder brief
Why exceeded: The creator's definition says Papers is a lightweight layer

                 Electron. Preload script (app/preload.js) bridging main and
                 renderer with Papers-named IPC channels.
Behavior       : Loads the world on launch. Registers all IPC handlers. Opens
                 the world view in a browser window. Native file/folder pickers
                 via Electron dialog. Real location opener via Electron shell.
Persistence    : Loads WorldStore from %APPDATA%\Papers\world on start
                 (overridable via PAPERS_WORLD_DIR env var).
Visible        : The full application experience.
Assumptions    : Electron is the shell; Windows is the primary target (AppData
                 path); node:fs for persistence.
Universal      : PARTIAL. The RESPONSIBILITY it fulfills (opening into a
                 persistent Backpack-identifying surface) is Papers-level. The
                 SPECIFIC TECHNOLOGY (Electron) is a current substrate choice,
                 not a Papers-universal requirement — see Section F2(a) and F6.
Tests          : Smoke boot test (npm run smoke).

-- E2. BACKPACK IDENTITIES AND ORGANIZATION --

What exists    : room.json per Backpack: {id, type:'backpack', title, createdAt,
                 lastEnteredAt, previousEnteredAt, description,
                 descriptionUpdatedAt}. WorldStore.createRoom, listRooms,
                 getRoomRecord, renameRoom, setRoomDescription.
Behavior       : Create a Backpack (generates id, creates directory); rename;
                 set description; list all Backpacks (world view).
Persistence    : rooms/<id>/room.json. Human-legible JSON, inspectable on disk.
Visible        : World view shows all Backpack cards with title, description
                 snippet, thing/missing/note counts, last activity line.
Assumptions    : Each Backpack has a title. The world view card shows
                 thingCount, missingCount, artifactCount — assumes these exist.
Universal      : The identity fields (id, title, type, timestamps) are Papers-
                 level. The counts (things, notes) assume the current Backpack's
                 furniture is universal. PARTIAL.
Tests          : world.test.js — world/room persistence and rename tests.

-- E3. ACTIVE BACKPACK SELECTION AND SWITCHING --

What exists    : IPC handlers room:get (marks entered, returns full view) and

                 Backpack surface at a time with a back button to the world view.
Behavior       : Entering a Backpack shifts previousEnteredAt to lastEnteredAt
                 (visit memory). Renderer shows one Backpack at a time.
Persistence    : lastEnteredAt and previousEnteredAt on room.json.
Visible        : Navigating from world view into a Backpack; the back button.
Assumptions    : One active Backpack at a time. (This is the only universal
                 runtime assumption per the creator's definition.)
Universal      : YES — this is the core Papers behavior.
Tests          : world.test.js — visit memory / previousEnteredAt tests.

-- E4. PERSISTENCE INFRASTRUCTURE --

What exists    : WorldStore class (app/world/store.js). Atomic file writes

Behavior       : All Papers state stored in Papers-owned JSON files. The world

Persistence    : The infrastructure itself. World directory at %APPDATA%\Papers\world.
Visible        : World directory is inspectable by the creator on the real machine.

Universal      : NEUTRAL SUBSTRATE — doesn't define Backpack ontology.
Tests          : world.test.js — all restart continuity tests run a fresh

F. IMPLEMENTATION RECOVERY CLASSIFICATION
================================================================================

This section was revised on 2026-07-10 to narrow F1 to only what
PAPERS_FOUNDER_BRIEF_V4 actually calls universal, and to make explicit that
"useful engineering" is not the same as "Papers core." No code changed in
this revision — only the classification.

-- F1. KEEP AS CURRENT CORE --

Limited strictly to behavior that directly implements Papers' narrow
responsibility: identify, organize, expose, enter, track, leave, and switch
Backpacks, one active at a time.

  (a) Persistent Backpack identity
      Evidence    : room.json identity fields (id, title, type, timestamps);
                    createRoom; listRooms.
      Reason      : Papers must identify and organize Backpacks. These are
                    identity fields, not furniture.
      Immediate action: RETAIN.

  (b) Backpack naming and organization
      Evidence    : renameRoom; setRoomDescription (naming/organizing, not the
                    description's use as "Backpack furniture" — see F3h for
                    the description's broader framing).
      Reason      : Organizing Backpacks is part of the narrow responsibility.
      Immediate action: RETAIN.

  (c) Visible access / launch / entry points
      Evidence    : World-view list of Backpacks; navigation into a Backpack.
      Reason      : Papers must expose Backpacks so the creator can enter them.
      Immediate action: RETAIN.

  (d) Current-Backpack tracking
      Evidence    : lastEnteredAt; markRoomEntered.
      Reason      : Papers must track which Backpack is/was active.
      Immediate action: RETAIN.

  (e) Leaving and switching
      Evidence    : room:get / room:refresh IPC; back-to-world-view navigation.
      Reason      : Papers must support leaving one Backpack and switching to
                    another.
      Immediate action: RETAIN.

  (f) One active Backpack at a time
      Evidence    : UI renders one Backpack surface at a time.
      Reason      : This is the ONLY universal runtime assumption stated in
                    PAPERS_FOUNDER_BRIEF_V4.
      Immediate action: RETAIN.

  NOT classified as core (moved below): Electron as a technology choice;
  WorldStore's persistence mechanics; truthfulness/honesty mechanisms;
  provenance; guarded actions; real-location affordances; artifacts; any AI
  engine behavior. These are good engineering, not Papers-universal identity
  — see F2 and F3.

-- F2. KEEP AS NEUTRAL OR CURRENT SUBSTRATE --

Useful engineering that the current Backpack (and potentially future ones)
may reuse. Explicitly NOT classified as Papers-universal core.

  (a) Electron application shell
      Evidence    : app/main.js, preload.js.
      Status      : Electron is the CURRENT shell, a technology choice for
                    this implementation — not Papers core. A different shell
                    could implement the same narrow responsibility.
      Immediate action: RETAIN as current substrate. Not to be treated as a
                    permanent commitment (see F6).

  (b) WorldStore persistence infrastructure
      Evidence    : store.js; atomic tmp+rename writes; JSON; %APPDATA% path.
      Status      : "WorldStore" is a historical implementation name, not
                    product ontology (see PAPERS_ONTOLOGY_CLARIFICATION_V1.txt).
                    The persistence mechanism itself (atomic JSON writes) is
                    reusable engineering.
      Immediate action: RETAIN as current substrate. Revisit format if scale
                    demands it — not yet investigated against alternatives.

  (c) AI engine adapter seam
      Evidence    : engine/index.js; runtimes/; prompts.js.
      Status      : Optional infrastructure for Backpacks that choose to use
                    AI. Not a Papers-universal requirement — AI architecture
                    is unspecified per PAPERS_FOUNDER_BRIEF_V4 Section 4. The
                    runtime-neutral adapter pattern is reusable if a future
                    Backpack wants AI and wants this style of seam.
      Immediate action: RETAIN as optional current substrate.

  (d) Honest failure / error-reporting behavior
      Evidence    : Engine unavailability reported honestly; missing-thing
                    status reporting; no-fake-reply discipline.
      Status      : Good engineering practice. NOT classified as universal
                    Backpack anatomy — a Backpack that makes no claims about
                    real-world state has nothing to be honest or dishonest
                    about. Where a Backpack does make such claims, honesty
                    about them is sound practice to reuse.
      Immediate action: RETAIN as a recommended pattern, not a universal law.

  (e) Test infrastructure
      Evidence    : app/test/; node:test; headless acceptance scripts.
      Status      : Reusable regardless of future Backpack variety.
      Immediate action: RETAIN.

-- F3. OPTIONAL BACKPACK MECHANISM --

Patterns and mechanisms specific to the current Backpack's chosen form.
Explicitly not required of any other Backpack. The creator may choose
different, fewer, or no such mechanisms for a new Backpack, including
choosing to give a Backpack unrestricted authority with no guard at all.

  (a) File/folder references (things.js, attachThing, refreshThings)
  (b) Source preview (previewThing)
  (c) Notes / artifacts (addArtifact, listArtifacts; room-note/working-note)
  (d) Conversation (conversation.json, appendConversation)
  (e) Activity / history (activity.json, appendActivity, navigable timeline)
  (f) Visit memory (previousEnteredAt, since-your-last-visit)
  (g) Pinned notes (setArtifactPinned)
  (h) Backpack description as a content field (setRoomDescription's use as
      Backpack-authored narrative, distinct from (b) in F1 which is the bare
      organizational act of naming)
  (i) Guarded action pattern (preview-before-execution, same-gathering-code
      for preview and execution) — MOVED HERE from the prior "neutral
      substrate" classification. The creator has explicitly established that
      a Backpack can be anything and may deliberately have unrestricted
      authority; guarding cannot be prescribed broadly. It remains an
      excellent pattern for a Backpack that wants it.
  (j) Provenance tracking on artifacts
  (k) Real-location affordances ("open real location")
  (l) Missing-state handling and reality-drift events

  For all of (a)-(l): RETAIN for the current Backpack. STOP EXPANDING without
  a specific creator-requested behavior for a specific Backpack. None of these
  may be assumed for a new Backpack without the creator specifying it.

-- F4. QUARANTINE FROM PRODUCT DIRECTION --

  (a) The Desk (desk.json, brief, desk items, working note, synthesizeDesk,
      getDeskView embedded in getRoomView)
      Evidence    : getDeskView() is called inside getRoomView() for EVERY
                    Backpack read — the Desk is structurally present in every
                    current Backpack, contradicting the Desk document's own
                    stated limit ("not a claim that every future Backpack is a
                    desk plus notes").
      Immediate action: STOP EXPANDING. Do not add Desk functionality to a new
                    Backpack until the creator specifically requests it.

  (b) getRoomView() returning the same furniture set for every Backpack record
      Evidence    : getRoomView() unconditionally assembles things, artifacts,
                    conversation, activity, and desk for any room id — there is
                    currently only one Backpack "shape" in code, so every
                    Backpack necessarily gets this furniture whether or not it
                    is wanted.
      Risk        : A future agent adding a second Backpack by calling
                    getRoomView() would inherit all of this furniture by
                    default, not by creator decision.
      Immediate action: No code change in this PR. Recorded here so a future
                    agent designing a second Backpack does not assume this
                    function's shape is the Backpack contract.

  (c) "World" / "room" naming in top-level code and IPC channels
      Evidence    : WorldStore, world.json, roomId, room:* IPC channels.
      Risk        : A future agent could infer "world" and "room" are active
                    product ontology from reading the code, contradicting
                    PAPERS_ONTOLOGY_CLARIFICATION_V1.txt.
      Immediate action: No rename required. Flagged so future agents check the
                    ontology doc rather than infer ontology from code names.

  (d) World-view cards assuming thingCount, missingCount, artifactCount
      Evidence    : listRooms() computes these counts for every Backpack card
                    in the world view, assuming every Backpack has things and
                    artifacts.
      Risk        : A future Backpack without things or artifacts would render
                    a card with zero/undefined counts, which could read as
                    "this Backpack type is incomplete" rather than "this
                    Backpack type doesn't use these concepts."
      Immediate action: No code change in this PR. Flagged for whoever designs
                    the second Backpack's world-view card to address.

  (e) The universal per-room AI action set (roomReply, generateRoomNote,
      synthesizeDesk) living in one shared engine/index.js
      Evidence    : All three actions are defined in the single engine seam
                    file, implicitly presented as "the" Papers AI actions.
      Risk        : A future Backpack with different AI needs might be
                    expected to fit into this same action set rather than
                    define its own.
      Immediate action: No code change in this PR. See F6(c) — this is also an
                    open architectural question, not yet a quarantine verdict.

-- F5. CANDIDATE FOR LATER REMOVAL --

  No immediate removals are authorized in this PR. This is a statement of
  current status, not a prerequisite: identifying removal candidates does NOT
  require building a second Backpack first. A removal candidate could equally
  be identified by the creator deciding a piece of F3 is not wanted, or by an
  agent finding a piece of F2/F3 that turns out to duplicate something
  reusable that a proper reuse investigation later surfaces. This section will
  be updated whenever such a finding occurs — it is not gated on any specific
  future build.

-- F6. UNRESOLVED --

  (a) Electron vs. other Windows technology stack
      Cannot be classified without knowing what other Backpacks will require.

  (b) JSON files vs. SQLite for persistence
      Current JSON is fine for one Backpack. Unknown at larger scale.

  (c) Whether the current Backpack's specific action set (roomReply,
      generateRoomNote, synthesizeDesk) remains in engine/index.js universally
      or gets moved to a Backpack-specific module as more Backpacks arrive.
